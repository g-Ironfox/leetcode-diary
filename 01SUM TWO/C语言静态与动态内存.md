# C 语言：静态、自动与动态内存

[Two Sum](./SUM%20TWO.md) · [Hash](./Hash.md) · [嵌入式内存管理](./嵌入式内存管理.md) · [计算机原理](./计算机原理.md)

> 以 `twoSum_hashmap.c` 与 `twoSum_hashmap_static.c` 为实例，分析 C 语言中对象的存储位置、存储期与生命周期，并讨论编译期固定大小与运行时动态分配两种策略在空间度量与工程性质上的差异。

# 一、内存度量：两版实现的空间占用

本节从字节计数出发，澄清一个常见的误解："固定数组版在 LeetCode 上显示的内存比动态版少约 1 MB，因此消除了约 1 MB 的哈希表开销"。

在上述评测环境中，

```text
sizeof(int)       = 4 字节
sizeof(HashEntry) = 8 字节
```

固定数组版声明了 `HASH_CAPACITY = 20001` 个 `HashEntry`，哈希槽占用的存储空间为：

$$20001 \times 8 = 160008\ \text{字节} \approx 156.26\ \text{KiB}$$

动态版的容量由输入规模决定：

$$\text{capacity} = \text{numsSize} \times 2 + 1$$

当 `numsSize = 10000` 时，`capacity = 20001`，槽位本体同样约为 156.26 KiB。动态版在堆上还额外分配了一个 `HashMap` 结构体（含指针与整型字段），其空间远小于 1 MB。

因此，在最大输入下，两版实现的哈希槽内存规模相同，差别仅在于存储位置与管理方式：

| 版本 | 哈希槽位置 | 最大输入时的槽位内存 |
|---|---|---:|
| 动态版 | 堆（heap） | 约 156.26 KiB |
| 固定数组版 | 栈（stack） | 约 156.26 KiB |

在小输入下，动态版反而更节省存储。例如 `numsSize = 10` 时，动态版仅申请 $21 \times 8 = 168$ 字节，而固定数组版始终占用约 156 KiB。

## 1.1 评测平台显示差值的可能来源

在线评测系统报告的"内存使用"通常是进程级别的统计量，其组成部分远不止应用层数据结构：

- 可执行文件、动态链接库和加载器的驻留页面；
- 测试框架的输入/输出缓冲区；
- 堆分配器按页面粒度或大小类别预保留的空间；
- 操作系统统计接口的采集粒度与舍入方式；
- 两次提交可能运行于不同进程实例，受到调度和缓存状态的影响。

因此，评测系统显示的 1 MB 级差值不应直接归因于"消除了哈希表占用的 1 MB"。严谨的比较应先通过 `sizeof` 与理论容量计算空间上界，再在同一环境中测量进程的峰值驻留内存，并排除分配器预保留等系统效应。

# 二、存储期的三种模型

日常讨论中的"静态分配"常指"数组大小在编译期确定、不使用 `malloc`"。在 C 标准的术语框架下，这一定义不够精确。本节区分自动存储期、静态存储期与动态存储期三种类别。

## 2.1 自动存储期

`twoSum_hashmap_static.c` 的实际实现方式是自动存储期，而非严格意义上的静态存储期：

```c
int* twoSum(...) {
    HashMap map;
}
```

`map` 具有自动存储期（automatic storage duration）：

- 进入声明所在的代码块时获得存储空间；
- 离开该代码块时自动失效；
- 在常见实现中分配于线程的调用栈上；
- 不可对其调用 `free`。

因此该实现更精确的命名应为"固定容量、自动存储期版本"。日常称其为"静态分配版"，仅是为了与 `malloc` 版本形成对照。该处的 `map` 并未使用 `static` 关键字。

## 2.2 静态存储期

```c
static HashMap map;
```

声明为 `static` 的对象具有静态存储期（static storage duration）：

- 程序启动前即已获得存储空间；
- 生命周期持续到程序终止；
- 通常位于可执行映像的数据段（.data）或 BSS 段；
- 默认初始化为零；
- 同样不可对其调用 `free`。

若将 `map` 声明为 `static`，可以避免在栈上占用约 156 KiB，但代价是丧失了可重入性：所有调用共享同一实例，递归、并发或多线程环境下可能产生覆盖。

## 2.3 动态存储期 — `malloc` 与 `calloc`

```c
HashMap* map = malloc(sizeof(HashMap));
map->entries = calloc(capacity, sizeof(HashEntry));
```

经由 `malloc` 或 `calloc` 获得的对象具有动态存储期（allocated storage duration）：

- 在运行时按需申请；
- 通常来自进程堆；
- 容量由运行时参数决定；
- 一直存活到显式调用 `free`；
- 遗漏 `free` 导致存储泄漏。

注意：动态版中 `createHashMap` 未检查 `malloc`/`calloc` 的返回值是否为 `NULL`。在内存充裕的环境中一般不会触发，但符合通用工程惯例的实现应在分配失败时显式处理。

# 三、内存区域的典型划分

C 标准从语义上规定了对象的存储期，但并不强制特定平台使用完全相同的物理布局。以下模型描述了现代通用平台的一种常见安排，用于辅助理解：

| 区域 | 典型内容 | 生命周期 | 管理方式 |
|---|---|---|---|
| 代码段（text） | 编译后的机器指令 | 整个进程 | 操作系统 |
| 只读数据段（rodata） | 字符串字面量、只读常量 | 整个进程 | 操作系统 |
| 数据段 / BSS | 全局变量、`static` 变量 | 整个进程 | 链接器与加载器 |
| 栈（stack） | 局部变量、调用帧 | 通常以函数返回为界 | 编译器生成的代码自动管理 |
| 堆（heap） | `malloc`/`calloc` 申请的对象 | 到 `free` 为止 | 程序员管理 |

两版 Two Sum 实现中，对象的归属关系如下：

```text
动态版：
栈                             堆
map（指针）  ──────────────>  HashMap 结构体
                                |
                                +────────> entries[capacity]

固定数组版：
栈
HashMap map
  +-- entries[HASH_CAPACITY]
  +-- capacity
```

值得区分的是：动态版中局部变量 `map` 本身是一个指针，通常位于栈上；它所指向的 `HashMap` 结构体和 `entries` 数组均位于堆上。指针与指向对象处于不同存储区域，这在 C 中是一种常态。

# 四、生命周期的对比

## 4.1 动态分配版

```text
twoSum 被调用
  → malloc 创建 HashMap 结构体
  → calloc 创建 entries 数组
  → 使用哈希表
  → free entries
  → free HashMap
  → 返回
```

优势：

- 容量由运行时 `numsSize` 决定，小规模输入仅消耗少量内存；
- 大对象置于堆上，不直接挤占线程栈；
- 每次调用拥有独立实例，易于支持递归与并发。

劣势：

- 分配与释放存在运行时开销；
- 必须处理分配失败的情况；
- 每条退出路径均需正确配对 `free`，否则产生泄漏；
- 通用分配器会产生元数据、对齐和碎片等额外开销。

## 4.2 固定数组版

```text
twoSum 被调用
  → 在栈帧中获得编译期定长的 HashMap
  → initHashMap 遍历并初始化所有槽位
  → 使用哈希表
  → 返回时自动失效
```

优势：

- 无需为哈希表调用 `malloc`/`free`；
- 生命周期由编译器管理，泄漏风险低；
- 存储连续，结构简单；
- 没有通用堆分配器引入的额外元数据。

劣势：

- 无论输入规模多小，均占用固定容量；
- 容量上限编码为宏，约束变化时需修改并重新编译；
- 约 156 KiB 的局部对象占用线程栈；
- 调用深度较大或栈空间受限时可能出现栈溢出。

# 五、返回数组为何仍需动态分配

固定数组版仅将哈希表改为编译期定长数组，结果的返回方式未变：

```c
int* result = malloc(2 * sizeof(int));
```

原因是 `twoSum` 返回后，其栈帧已失效，局部数组的生命周期随之终止：

```c
int result[2];
return result;  /* 未定义行为：result 所在存储已失效 */
```

采用 `static int result[2]` 可以绕过生命周期限制，但所有调用将共享同一块存储，后一次调用会覆盖前一次的结果，且不适合并发场景。LeetCode 的 C 接口约定由调用方 `free` 返回的数组，因此这里继续使用 `malloc` 是符合接口契约的做法。

# 六、嵌入式系统的延伸讨论

MCU、RTOS 和实时 Linux 系统对内存管理提出了更严格的约束：存储容量上界必须在设计阶段可证明，分配耗时必须有界，长期运行不可因碎片而恶化。关于 MCU/MPU 的典型约束、外部碎片与内部碎片的成因、通用堆的时序不确定性问题，以及固定块内存池、Arena 分配器、环形缓冲区等替代方案，另文讨论：[嵌入式内存管理：静态规划、堆碎片与内存池](./嵌入式内存管理.md)。

其中纠正了一个常见误解：链表这一数据结构本身并不产生堆碎片；为每个节点分别调用通用 `malloc`，并在不同时间以不同顺序 `free`，才是导致外部碎片的直接原因。

# 七、选择策略

两种方式的适用条件可归纳如下。

编译期定长数组更适用的情况：

- 最大容量在编译期已确定，且运行时不会超出该上界；
- 对象规模较小，栈空间充裕；
- 需要避免动态分配失败和手动释放带来的管理复杂度；
- 运行环境预先规划了所有存储区域。

动态分配更适用的情况：

- 容量取决于运行时输入，且规模变化范围较大；
- 最大对象超出线程栈的可用空间；
- 需要对象在创建它的函数返回后继续存活；
- 需要灵活创建和销毁多个实例，或支持不同的并发策略。

选择的核心不在于"静态快"或"动态省"这类笼统判断，而在于同时权衡以下维度：

```text
容量何时已知（编译期 vs 运行时）
  × 对象需要存活多久
  × 内存的所有权与释放责任由谁承担
  × 栈空间是否足以承载最坏情况下的局部对象
  × 是否需要递归、可重入或并发访问
```

# 八、回到 Two Sum

两版实现具有相同的渐进复杂度：

$$T(n) = O(n),\quad S(n) = O(n)$$

固定数组版的哈希表长度写入了一个编译期常量，但该常量由题目约束的最大 $n$ 所决定。若分析一系列输入规模不断增大的问题实例，该长度仍需随允许的输入上界增长，因此不应将其空间复杂度误记为 $O(1)$。

综上，固定数组版并未消除约 156 KiB 的哈希表存储——它用编译期确定的上限替代了运行时的动态分配，并将哈希表从堆迁移到了栈。评测平台显示的内存差值不足以作为"代码节约了 1 MB"的证据。
