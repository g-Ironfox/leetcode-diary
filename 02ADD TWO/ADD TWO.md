# Add Two Numbers 解题笔记

## 题目

给你两个 **非空** 的链表，表示两个非负的整数。它们每位数字都是按照 **逆序** 的方式存储的，并且每个节点只能存储 **一位** 数字。

请你将两个数相加，并以相同形式返回一个表示和的链表。

你可以假设除了数字 0 之外，这两个数都不会以 0 开头。

```
示例 1：
输入：l1 = [2,4,3], l2 = [5,6,4]
输出：[7,0,8]
解释：342 + 465 = 807.

示例 2：
输入：l1 = [0], l2 = [0]
输出：[0]

示例 3：
输入：l1 = [9,9,9,9,9,9,9], l2 = [9,9,9,9]
输出：[8,9,9,9,0,0,0,1]
```

提示：
```
每个链表中的节点数在范围 [1, 100] 内
0 <= Node.val <= 9
题目数据保证列表表示的数字不含前导零
```

## 摘要

这道题比 Two Sum 简单多了，属于"模拟题"——不需要任何高级数据结构，就是把小学竖式加法翻译成链表遍历。当时唯一纠结的点是：

> 我以为要双向链表，结果发现单链表就够了。

原因是题目把数字**逆序**存储（个位在头），从头往后遍历天然就是"从低位往高位加"，方向白送，根本不需要往回走。详见下文第三节。

## 一、核心思路：模拟竖式加法

小学加法怎么算？从个位开始，逐位相加，满十进一：

```
    3 4 2
  + 4 6 5
  -------
    8 0 7    ← 2+5=7，4+6=10 写 0 进 1，3+4+1=8
```

链表版一模一样，只不过数字被拆成一个一个节点，而且**逆序**存放：

```
l1:  2 -> 4 -> 3     （个位 2 在头）
l2:  5 -> 6 -> 4     （个位 5 在头）
      ↓    ↓    ↓
      7    0    8     （进位 1 传给百位）
```

所以遍历链表头到尾，就是在做竖式从低位到高位。

### 三个关键点

**1) dummy 哨兵节点**

如果不用 dummy，第一个节点要单独 `if` 判断"这是不是头节点"，很啰嗦。用一个不存数据的哨兵节点开头，后面所有节点统一走"`cur->next = 新节点`"，最后 `return dummy->next` 跳过哨兵即可。

> 用 dummy 的本质：把"头节点"这个特殊情况，变成和普通节点一样的统一处理。

**2) carry 进位**

每轮计算：

```c
int sum = carry;        // 先加上进位
sum += l1->val;         // 再加 l1 当前位
sum += l2->val;         // 再加 l2 当前位

carry = sum / 10;       // 进位：满十进一
cur->val = sum % 10;    // 当前位只存个位数
```

因为每位数字最大 9，两个 9 加进位 1 最多 `9+9+1 = 19`，所以 `carry` 只可能是 0 或 1。

**3) 循环条件：`l1 || l2 || carry`**

两个链表长度不一定相同（示例 3 一个 7 位一个 4 位），短的走完了就当它的位是 0。同时最后一位可能产生进位（`99 + 1 = 100`，多出最高位的 1），所以循环条件要把进位也算上：

```c
while (l1 != NULL || l2 != NULL || carry != 0) {
    ...
}
```

## 二、完整代码

```c
#include <stdlib.h>

struct ListNode {
    int val;
    struct ListNode *next;
};

struct ListNode* addTwoNumbers(struct ListNode* l1, struct ListNode* l2) {
    struct ListNode *dummy = (struct ListNode *)malloc(sizeof(struct ListNode));
    dummy->next = NULL;              // 哨兵节点
    struct ListNode *cur = dummy;
    int carry = 0;

    while (l1 != NULL || l2 != NULL || carry != 0) {
        int sum = carry;
        if (l1 != NULL) { sum += l1->val; l1 = l1->next; }
        if (l2 != NULL) { sum += l2->val; l2 = l2->next; }

        carry = sum / 10;
        cur->next = (struct ListNode *)malloc(sizeof(struct ListNode));
        cur = cur->next;
        cur->val = sum % 10;
        cur->next = NULL;            // 新节点 next 必须置 NULL
    }

    struct ListNode *result = dummy->next;
    free(dummy);                     // 释放哨兵，避免内存泄漏
    return result;
}
```

### 复杂度

| | 复杂度 | 说明 |
|---|---|---|
| 时间 | $O(\max(n, m))$ | 每个节点至多访问一次，$n$、$m$ 分别为两链表长度 |
| 空间 | $O(1)$ | 只用了常数个临时变量（返回的链表不算额外空间） |

## 三、为什么单链表就够了？（我的纠结）

双向链表唯一的优势是**能往回走**。而这道题的加法顺序是：

```
个位 → 十位 → 百位 → ……
```

题目把数字**逆序**存储，即**链表的头就是最低位**。于是：

> 从头到尾遍历的方向 = 加法从低位到高位的方向。

我们只需要往前走，永远不需要回头，`next` 就够了，`prev` 纯属多余。

**什么时候才需要双向链表 / 栈？** 如果题目改成**正序存储**（高位在头），个位在尾巴，那就得：

1. **反转链表**，按老办法加完再反转回来；或
2. 用**栈**，把两链表各压一遍再弹出（弹出顺序就是低位在前）；或
3. 用**双向链表**直接从尾部开始加。

另外还有个更硬的理由：LeetCode 的题面**已经定义死了**

```c
struct ListNode {
    int val;
    struct ListNode *next;
};
```

输入类型是固定的单链表，接口就长这样，想改双向也没得改。

> 一句话：**逆序存储 + 从头遍历 = 天然的低位在前，单链表白送方向。**

## 四、易错点清单

1. **`next` 置 NULL**：每 malloc 一个新节点，`next` 是野指针，必须手动置 `NULL`，否则遍历会越界。这也是上一题《头文件问题》里 `NULL` 来自 `<stdlib.h>` 的延续。
2. **最后一位进位**：`999 + 1 = 1000`，会多出一个最高位的 1。忘记把 `carry` 写进循环条件就会丢位。
3. **长度不一致**：短的链表走完后 `l1->val` 会解引用空指针，必须先判 `l1 != NULL` 再加。
4. **`free(dummy)`**：C 没有 GC，malloc 了就要 free。哨兵节点用完了记得释放，否则内存泄漏。
5. **LeetCode 提交时不用写 `#include <stdlib.h>`**：官方已自动包含，本地 VS Code 才需要（详见《头文件问题.md》）。

以上是编码细节层面的坑。下面跳出代码，从算法理论角度审视这道题的上下限。

## 五、算法分析

- **时间复杂度**：$O(\max(n, m))$ — 必须遍历每一位，无法更优。
- **空间复杂度**：取决于实现方式——建新链表则 $O(n)$，原地修改则可压到 $O(1)$。

那么原地修改具体怎么做？下面把优化版拆成四个阶段逐一分析。

---

## 六、优化原理详解：四阶段策略

优化版的代码把整个加法过程拆成**四个阶段**，每个阶段针对不同的场景做极致优化：

```
        l1 和 l2 都有？
             │
      ┌──────┴──────┐
     是              否（至少一个走完）
      │              │
 第一阶段           谁更长？
 直接改 l1.val     ┌──┴──┐
 两个指针都前进   l2更长  l1更长
      │              │      │
      │         第二阶段   直接进入
      │         把l2接到    第三阶段
      │         l1尾部
      │              │
      └──────┬───────┘
             │
         第三阶段
     处理剩余节点 + carry
     （只需加进位，不用加 l2 了）
             │
         还有进位？
        ┌───┴───┐
       是       否
        │        │
   第四阶段     结束
   唯一一次
   malloc 新节点
```

### 第一阶段：双链表并行，就地修改

```c
while (l1 != NULL && l2 != NULL) {
    int sum = l1->val + l2->val + carry;
    l1->val = sum % 10;    // 直接覆盖 l1 的值
    carry = sum / 10;
    prev = l1;
    l1 = l1->next;
    l2 = l2->next;
}
```

这是两个链表"重叠"的部分。每走一步只做三件事：加、改值、前进。没有 `malloc`，没有新建节点，连 `dummy` 哨兵都不要——因为 `l1` 的第一个节点天然就是结果的第一个节点。

> **关键**：用 `prev` 记住 l1 的最后一个节点。它有两个用途：① 第二阶段"接"l2 时需要知道接在哪；② 第四阶段 `malloc` 新节点时需要知道挂在哪。

### 第二阶段：l2 比 l1 长？直接"拼接"

```c
if (l2 != NULL) {
    prev->next = l2;   // l2 剩余部分挂到 l1 尾部
    l1 = l2;           // 让 l1 指向这些接过来的节点
}
```

这是优化版最精妙的一步。常规版遇到 l2 更长时，需要**逐节点 malloc 复制** l2 的剩余部分。但仔细想想：

- l2 的剩余节点已经存在了，值也对（除了可能受进位影响）
- 我们只需要处理进位，不需要复制

所以直接把 l2 的尾巴"嫁接"到 l1 后面。**0 次 malloc，O(1) 时间**，链表就变长了。然后让 `l1` 指向这些接过来的节点，第三阶段统一处理进位。

> l1 更长的情况呢？不需要第二阶段——l1 剩余节点本来就在那，直接进第三阶段。

### 第三阶段：只处理进位，不再加 l2

```c
while (l1 != NULL && carry != 0) {
    int sum = l1->val + carry;   // 注意：只加 carry，不加 l2
    l1->val = sum % 10;
    carry = sum / 10;
    prev = l1;
    l1 = l1->next;
}
```

此时 l2 已经走完了（要么在第一阶段同时走完，要么在第二阶段被接过来后也走完了），所以 `sum` 里只有 `l1->val + carry`，不再加 `l2->val`。

还有一个重要优化：循环条件是 `l1 != NULL && carry != 0`。如果进位在中途就消了（比如 1002 + 3 = 1005，进位只传到千位就没了），**直接跳出**，剩下的高位节点原封不动——值本来就是对的不需要改。

### 第四阶段：唯一的 malloc

```c
if (carry != 0) {
    prev->next = (struct ListNode *)malloc(sizeof(struct ListNode));
    prev->next->val = carry;
    prev->next->next = NULL;
}
```

两个链表都走完了，但还有进位（如 999 + 1 = 1000，最高位的 1）。这是**整个算法唯一一次 `malloc`**，且只在进位溢出时才触发。绝大多数测试用例根本走不到这里。

### 为什么这么快？一张图看懂

```
常规版:  每位: malloc → 赋值 → 链接 → next=NULL
         100 位 = 100 次 malloc（每次都要进内核、抢锁）

优化版:  直接改 l1.val，指针往后挪
         100 位 = 0 次 malloc（纯 CPU 运算，不进内核）

         只有最高位溢出时: 1 次 malloc
```

`malloc` 的代价不是 CPU 运算，而是**系统调用 + 内存分配器内部锁**。LeetCode 跑 100 个测试用例，常规版可能 malloc 几百到上千次，每一次都要进出内核态、争抢全局堆锁。优化版把这上千次系统调用砍到 0~1 次，所以能从 8ms 直接干到 0ms。

### 什么时候不能用这种优化？

- **不允许修改输入**：如果题面或面试官要求"不能改输入链表"，那就只能老老实实建新链表。
- **多线程环境**：其他线程可能同时读 l1/l2，原地修改会导致数据竞争。
- **需要保留原始数据**：如果调用方后续还要用 l1 和 l2 做别的事，就不能破坏它们。

搞清楚了优化版的内部机制，下面把常规版和优化版放在一起，用数据和流程图直观对比。

## 七、两种实现对比

| | `1.c` (常规版) | `2_optimized.c` (优化版) |
|---|---|---|
| **策略** | 每次 `malloc` 新节点，构建全新结果链表 | 复用 l1 节点，原地修改值 |
| **malloc 次数** | ≈ $\max(n, m)$ 次（每位一次 + dummy） | ≤ 1 次（仅进位溢出时） |
| **空间复杂度** | $O(\max(n, m))$ | $O(1)$（不计返回链表） |
| **副作用** | 不修改输入 | ⚠️ 会**破坏** l1 和 l2 的原始数据 |

### LeetCode 跑分对比

| | `1.c` (常规版) | `2_optimized.c` (优化版) |
|---|---|---|
| **执行用时** | 8 ms | **0 ms** |
| **用时击败** | 6.47% | **100.00%** |
| **消耗内存** | 13.34 MB | **12.72 MB** |
| **内存击败** | 14.38% | **96.51%** |

> 仅"不 malloc"这一个改动：用时 8ms → 0ms，内存 13.34 MB → 12.72 MB，排名从垫底蹿到榜首。

### 常规版 (`1.c`) 流程

```
输入: l1=[2→4→3], l2=[5→6→4]

创建 dummy → 逐位 malloc 新节点:

    2+5=7, carry=0 → newNode(7)
    4+6=10, carry=1 → newNode(0)
    3+4+1=8, carry=0 → newNode(8)

结果: 7→0→8  (全新链表，l1、l2 原封不动)
```

### 优化版 (`2_optimized.c`) 流程

```
输入: l1=[2→4→3], l2=[5→6→4]

第一阶段 (l1 和 l2 都有节点):
    2+5=7 → 直接改 l1.val=7
    4+6=10 → l1.val=0, carry=1
    3+4+1=8 → l1.val=8, carry=0

l2 先走完，l1 剩余节点直接保留（不用动）。

结果: 7→0→8  (就是原来的 l1，值被改了)
```

### l2 比 l1 长的情况

```
l1=[1], l2=[9→9→9]

第一阶段: 1+9=10 → l1.val=0, carry=1, l1 走完了
第二阶段: l1=NULL, l2 还有 [9→9] → prev->next = l2 直接接上
第三阶段: 继续处理接过来的 [9→9] + carry

结果: 0→0→0→1  (l1 尾部连着 l2 的节点)
```

跑分差距悬殊，但两种实现的算法复杂度是一样的——都是 $O(n)$。那这 8ms 到底差在哪？

## 八、为什么 C 语言排名差距这么大？

第六章已经从 `malloc` 系统调用的角度解释了核心原因，这里再从 LeetCode 评测环境的角度补充两点：

1. **`malloc` 拖慢的不只是时间**：每个 `malloc` 节点都有元数据开销（通常 16-32 字节），常规版多分配几百个节点 → 内存占用明显上升，内存排名也跟着垫底。
2. **排名百分比的"欺骗性"**：C 语言的大量提交都集中在 0-4ms，你 8ms 就会被挤到后 6%。不是算法差，是大家在一条极窄的跑道上比毫秒。

---

## 九、核心技巧总结

- **哨兵节点 (dummy)**：常规版用它避免处理"第一个节点为空"的边界情况。
- **原地修改 (in-place)**：优化版的核心思想——链表题中如果允许破坏输入，优先考虑复用已有节点。
- **进位处理**：`carry = sum / 10`，当前位 `sum % 10`，循环条件包含 `carry != 0` 以防最高位进位（如 99+1=100）。
- **链表拼接**：l2 比 l1 长时，直接把 l2 剩余部分"接"到 l1 尾部，免去逐节点复制。
