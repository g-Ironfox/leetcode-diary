# 嵌入式内存管理：静态规划、堆碎片与内存池

[Two Sum](./SUM%20TWO.md) · [Hash](./Hash.md) · [C 语言内存](./C语言静态与动态内存.md) · [计算机原理](./计算机原理.md)

> 从 MCU 与 MPU 的硬实时约束出发，分析通用堆分配器在嵌入式场景中的失效模式——外部碎片、内部碎片与时间不确定性——并讨论固定块内存池、Arena 分配器、环形缓冲区等替代方案的原理、适用条件与设计折衷。

# 一、确定性：嵌入式内存管理的核心约束

本文的"MPU"指 Microprocessor Unit（微处理器），非 Memory Protection Unit（内存保护单元）。两个概念在文献中常有交叉，此处依上下文区分。

桌面程序的内存管理通常以平均吞吐量和开发效率为主要优化目标。嵌入式系统引入了一组不同的约束：

- 存储容量必须在最坏情况下仍有保证，而非仅在统计意义上够用；
- 分配与释放操作的时间上界必须在设计阶段可证明；
- 系统需持续运行数月或数年，性能不可随运行时间而退化；
- 故障模式必须是可分析的，而非仅在特定操作序列下才暴露。

因此，嵌入式内存管理的核心问题并非"总共有多少 RAM"，而是：

> 内存使用上界和每次分配的最坏耗时，能否在程序运行之前得到证明。

## 1.1 裸机 MCU 的典型约束

裸机 MCU 或小型 RTOS 系统通常处于以下条件：

- SRAM 容量在几 KiB 至几百 KiB 量级；
- 无虚拟内存和交换空间，RAM 耗尽后无操作系统层面的兜底机制；
- 堆与栈常共享同一块连续 SRAM，双方增长方向相反时可能互相挤压；
- 各任务栈大小需提前配置，栈溢出可能静默破坏相邻内存区域；
- 中断服务程序（ISR）和硬实时任务要求执行时间有硬上界；
- 短期功能测试无法暴露慢性碎片——系统可能运行数周后才首次因碎片耗尽而分配失败。

在此约束下，嵌入式项目通常于链接阶段规划内存布局：

```text
Flash：代码（.text）、只读常量（.rodata）
SRAM ：已初始化数据（.data）、未初始化数据（.bss）、各任务栈、固定缓冲区、可选堆
```

链接器生成的 map 文件可提供各段的字节占用。这使得"最坏情况下会消耗多少 RAM"可以在运行前得到回答，而非仅依赖运行时观测。

## 1.2 运行 Linux 的 MPU 为何仍面临同类问题

具备 MMU 和虚拟内存的微处理器平台拥有更充裕的 RAM，但约束并未完全消失：

- 实时控制线程仍然无法容忍不可预测的分配延迟；
- 内存压力下内核可能触发页面回收、换出或 OOM Killer，其时序和结果不适合硬实时路径；
- DMA 缓冲区、硬件编解码器与某些外设要求物理连续的内存；
- 长期运行的服务进程仍可能因泄漏或碎片而逐渐退化；
- 安全关键系统（如 ISO 26262、DO-178C 所约束的领域）要求资源上界可静态证明。

工程中常见的策略并非"整个系统禁止动态内存"，而是：

> 初始化阶段允许动态分配；进入稳态运行循环后，不再调用通用 `malloc`/`free`。

这平衡了启动阶段的配置灵活性与运行阶段的时序确定性。

## 1.3 嵌入式语境中"静态分配"的典型形式

嵌入式工程中的静态分配通常指：

```c
static Message message_pool[MAX_MESSAGES];
static uint8_t uart_rx_buffer[UART_RX_SIZE];
```

这类对象具有静态存储期，位于 `.bss` 或 `.data` 段，而非任何任务的栈上。其容量、地址范围和生命周期在构建时即已确定。

为避免堆而将大型数组声明为函数局部变量，在 MCU 工程中并不常见——大局部变量同样可能导致栈溢出。更典型的做法包括：

- 文件作用域或模块级的 `static` 缓冲区；
- 由调用方提供存储空间的接口设计（caller-provided buffer）；
- 固定大小内存池；
- 各模块持有自己的预分配工作区；
- 使用 RTOS 提供的静态创建接口（`xQueueCreateStatic` 等）。

# 二、堆碎片的成因与分类

## 2.1 外部碎片

先给出该问题的精确表述：

> 链表这一数据结构不直接产生堆碎片。为每个节点分别调用通用 `malloc`，并以不同顺序 `free`，才是导致外部碎片的根因。

链表完全可以使用固定数组与整数下标实现，此时不发生通用堆碎片。反之，即使不使用链表，只要以不同大小、不同顺序频繁申请和释放对象，通用堆同样可能碎片化。

一个简化的示例：假设堆上依次分配四个块，

```text
[ A:100 ][ B:200 ][ C:100 ][ D:200 ]
```

释放 `B` 和 `D` 后：

```text
[ A:100 ][ 空闲:200 ][ C:100 ][ 空闲:200 ]
```

此时总空闲量为 400 字节，但若请求一块 300 字节的连续内存，分配仍可能失败——连续空闲块的最大长度为 200。

这种现象称为外部碎片（external fragmentation）：

```text
空闲内存总量 ≥ 请求大小
但所有空闲块均不连续，无法满足单次分配需求
```

若分配器支持相邻空闲块的合并（coalescing），相邻空闲区域可被合并；但上例中被 `C` 隔开的两块无法合并。

## 2.2 内部碎片

通用分配器通常会对请求大小进行对齐，并按内部大小类别取整。例如请求 13 字节，实际分配的块可能占用 16 字节甚至更多：

$$\text{实际占用} > \text{用户请求的有效载荷}$$

块内部无法用于其他分配的剩余空间称为内部碎片（internal fragmentation）。此外，每个分配块通常携带若干字节的管理元数据（块大小、空闲链表指针等）。

对于一个仅包含少量有效载荷的链表节点：

- `next` / `prev` 指针本身即占用 4 或 8 字节；
- 地址对齐可能引入填充字节；
- 堆分配器的块头可能额外消耗 8–16 字节；
- 外部碎片与内部碎片同时存在。

在 32 位 MCU 上，一个有效载荷仅几个字节的节点，其总占用可能达到有效载荷的数倍。

## 2.3 长期运行的退化模式

若对象的分配大小不同且生命周期交错，堆的布局将随分配/释放的历史持续变化。系统启动时的一大片连续空闲区，经过数周运行后可能退化为大量不连续的小空洞。

这产生了一类难以在实验室中复现的故障：

```text
系统仍有可观的空闲内存总量
  → 某次较大的连续分配请求失败
  → 故障的发生依赖于此前长时间的操作序列
  → 短期功能测试无法覆盖
```

链表常与此类故障关联，因为常见实现为每个节点单独分配内存，且插入/删除的时序取决于运行时事件。但根因在于通用堆分配模式，而非链式结构本身。

## 2.4 时间不确定性

`malloc` 的操作并非总是常数时间的指针移动。通用分配器可能需要：

- 沿空闲链表搜索合适大小的块；
- 对较大空闲块进行分割；
- 在 `free` 时定位并合并物理相邻的空闲块；
- 在多线程环境中获取锁；
- 在操作系统管理的堆上向内核请求更多页面。

具体行为取决于分配器实现（dlmalloc、ptmalloc、tcmalloc、jemalloc 等）及当前的堆状态。普通程序关注平均分配延迟，而硬实时系统关注最坏情况执行时间（WCET）。即使分配最终成功，耗时的波动也可能导致截止时间违约。因此，ISR 和硬实时控制循环通常避免调用通用 `malloc`/`free`。

# 三、替代方案

## 3.1 固定块内存池

预先准备一组大小相同的节点：

```c
#define NODE_COUNT 64

typedef struct Node {
    int value;
    struct Node* next;
} Node;

static Node node_pool[NODE_COUNT];
```

维护一条空闲节点链表。分配时从空闲链表摘取首节点，释放时将其插回链表：

- 无外部碎片：所有块大小相同，不存在"找不到足够大的连续块"的问题；
- 分配与释放均为 $O(1)$；
- 代价：同时存活的节点数不能超过 `NODE_COUNT`，且节点大小固定。

值得指出的是，空闲链表仅用于管理预分配数组中的节点，并未逐节点调用 `malloc`——"使用链表"与"产生堆碎片"并不等价。

## 3.2 数组加整数下标

将节点存储在数组中，用整数下标代替指针：

```c
typedef struct {
    int value;
    int next_index;
} Node;

static Node nodes[NODE_COUNT];
```

此方案容量固定、内存布局连续，便于序列化、调试和静态分析。语义上它仍表达链表关系，只是节点引用方式从内存地址变为数组索引。

## 3.3 Arena / 区域分配器

预先获取一块连续内存，此后仅顺序向前分配；当某一阶段或某一帧结束时，将整个区域一次性重置：

```text
[已分配........][下一可用位置][剩余........]
```

- 分配操作极快（通常仅移动一个指针）；
- 不会因交错释放而产生外部碎片；
- 代价：通常不能单独释放其中某个对象。适用于生命周期相同的一批临时对象（如一帧渲染数据、一次网络请求的解析中间结果）。

## 3.4 环形缓冲区

串口接收、网络包缓冲和传感器采样等场景通常使用固定大小的环形缓冲区。生产者写入、消费者读出，避免为每一帧数据单独分配内存。

环形缓冲区适用于 FIFO 数据流，但需要明确定义缓冲区满时的策略：覆盖旧数据、丢弃新数据，还是触发错误处理。

## 3.5 多尺寸固定池与实时分配器

若对象存在几种不同的典型尺寸，可分别建立小块池、中块池和大块池。该思路与 slab 分配器类似：以一定的内部碎片为代价，换取无外部碎片和可预测的分配时间。

某些实时系统采用具有最坏时间上界的专用分配器（如 TLSF）。但需注意：实时分配器仅改善时间可预测性和碎片控制，不能使有限的物理 RAM 容量增加，也不能替代对最坏情况下同时存活对象数量的静态分析。

# 四、嵌入式内存管理的设计原则

比"一律禁止 `malloc`"更精确的工程原则可归结为：

1. 计算最坏情况下同时存活的对象数量及每类对象的大小。
2. 硬实时路径和 ISR 中禁止调用通用动态分配器。
3. 可在初始化阶段确定的资源，在启动时一次性申请或直接静态预留。
4. 频繁创建和销毁、且大小固定的对象使用内存池管理。
5. 为每个任务栈保留余量；通过栈水位标记、内存保护单元（MPU）或栈哨兵检测溢出。
6. 为每种资源池定义明确的耗尽策略——不可默认"池永远不会满"。
7. 审查链接器 map 文件、堆峰值测量、栈峰值测量及长期压力测试结果。

静态预留也并非没有代价：容量估计过大意味着 RAM 被永久占用而无法用于其他目的，估计过小则意味着固定失败。关键仍然是容量分析与明确的失败策略，而非"静态"或"动态"的标签。

# 五、回到 Two Sum

若将当前 Two Sum 固定数组版移植到 MCU 环境，工程上更合理的做法并非保留函数内约 156 KiB 的局部 `HashMap`，而是：

- 根据目标设备的 SRAM 总量和输入上限重新确定哈希表容量；
- 将工作区设计为文件作用域的 `static` 数组、调用方提供的缓冲区，或模块专用的固定内存池。

这样才能同时控制栈深度、总 RAM 占用上界以及并发访问的安全语义。嵌入式系统中的内存管理，本质上不是"堆与栈"的二选一，而是在设计阶段能否回答以下问题：

> 每块内存的容量是多少？由谁拥有？生命周期多长？最坏情况下的分配耗时是多少？耗尽时系统如何反应？
