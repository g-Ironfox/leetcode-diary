# 滑动窗口的工程应用

## 一、从算法题走向工程系统

在算法题中，滑动窗口通常用于寻找满足条件的连续子数组或子串。在工程系统中，它更常用于回答：

> 最近一段时间或最近一批数据的状态是什么？

例如：

- 最近 20 个交易日的平均价格；
- 最近 5 分钟的接口错误率；
- 最近 1000 个预测结果的均方误差；
- 最近 60 秒内某个用户发送了多少请求；
- 最近一段传感器数据的均值、方差和峰值。

工程中的窗口通常有两种定义：

1. **按数量定长**：最近 `k` 条数据，例如最近 20 个交易日；
2. **按时间定长**：最近 `T` 秒的数据，例如最近 5 分钟。

两者的统一模型是：

```text
新数据从右侧进入
过期数据从左侧离开
更新并查询当前窗口状态
```

## 二、为什么工程系统需要滑窗

假设需要计算长度为 `k` 的每个窗口的平均值。

如果每到一个新数据点，都重新遍历最近 `k` 个元素，处理 `n` 个数据点的时间复杂度为：

$$
O(nk)
$$

如果维护窗口和，则更新公式为：

$$
S_t=S_{t-1}+x_t-x_{t-k}
$$

每个新数据点只需加入一个值、删除一个值，总时间复杂度降为：

$$
O(n)
$$

对于持续运行的数据流，每次更新通常只需要 $O(1)$。

这也是工程滑窗的核心价值：**把重复的批量计算改造成增量计算。**

## 三、工程滑窗的统一接口

一个滚动统计组件通常需要三个操作：

```text
add(newValue)       新数据进入窗口
remove(oldValue)    过期数据离开窗口
query()             查询当前统计量
```

如果这三个操作都能高效完成，就可以持续处理数据流，而不必保存和重新计算全部历史数据。

窗口通常还需要保存：

- 当前元素数量；
- 数据到达时间；
- 一个队列或环形缓冲区；
- 当前统计状态；
- 窗口尚未填满时的处理规则。

## 四、股票与量化指标

定长滑窗本质上是在维护最近 `k` 个价格、收益率、成交量或预测误差的滚动统计量，因此非常适合计算金融时间序列指标。

### 1. 简单移动平均 SMA

设窗口包含最近 `k` 个价格：

$$
x_{t-k+1},\ldots,x_t
$$

维护窗口和：

$$
S_t=S_{t-1}+x_t-x_{t-k}
$$

简单移动平均为：

$$
SMA_t=\frac{S_t}{k}
$$

每次更新由重新累加的 $O(k)$ 降为 $O(1)$。

```c
double updateSMA(double previousSum, double newPrice,
                 double expiredPrice, int windowSize)
{
    double currentSum = previousSum + newPrice - expiredPrice;
    return currentSum / windowSize;
}
```

实际组件不能只返回平均值，还应保存更新后的 `currentSum`，供下一轮继续计算。

### 2. 滚动 MSE

设实际值为 $y_i$，预测值为 $\hat y_i$。单个样本的平方误差为：

$$
e_i=(y_i-\hat y_i)^2
$$

维护窗口误差平方和：

$$
E_t=E_{t-1}+(y_t-\hat y_t)^2-(y_{t-k}-\hat y_{t-k})^2
$$

滚动均方误差为：

$$
MSE_t=\frac{E_t}{k}
$$

它可以用于：

- 监控股票预测模型近期是否退化；
- 比较不同模型在当前市场状态下的误差；
- 触发模型重训或切换策略；
- 检测近期误差是否突然上升。

```c
double squaredError(double actual, double predicted)
{
    double difference = actual - predicted;
    return difference * difference;
}
```

窗口中只需维护误差平方和以及过期样本的平方误差。

### 3. 滚动方差与标准差

可以同时维护：

$$
S=\sum x_i,\qquad Q=\sum x_i^2
$$

总体方差为：

$$
\sigma^2=\frac{Q}{k}-\left(\frac{S}{k}\right)^2
$$

标准差为：

$$
\sigma=\sqrt{\sigma^2}
$$

滚动标准差常用于估计近期波动率。

但是，这个公式可能发生浮点数消减误差：当数据值很大而方差很小时，两个接近的大数相减会损失精度。工程系统中应根据精度要求考虑：

- 使用 `double` 而不是 `float`；
- 对数据进行中心化或缩放；
- 使用更稳定的在线方差或滚动方差算法；
- 对计算结果中很小的负数进行误差修正，但不能借此掩盖真正的计算错误。

### 4. 布林带

布林带建立在移动平均与滚动标准差之上：

$$
Middle_t=SMA_t
$$

$$
Upper_t=SMA_t+m\sigma_t
$$

$$
Lower_t=SMA_t-m\sigma_t
$$

常见参数是窗口大小 `20`、标准差倍数 `2`。它只是在同一个窗口状态上组合多个统计结果。

### 5. 滚动 VWAP

维护窗口成交额与成交量：

$$
A=\sum Price_i\cdot Volume_i
$$

$$
V=\sum Volume_i
$$

则成交量加权平均价为：

$$
VWAP=\frac{A}{V}
$$

新交易进入时增加 `price * volume` 和 `volume`，旧交易过期时减去相同贡献。

计算前必须处理 $V=0$ 的情况。

### 6. 滚动相关系数与 Beta

对于股票收益率 $x_i$ 和市场收益率 $y_i$，可以维护：

$$
\sum x_i,\quad \sum y_i,\quad \sum x_i^2,\quad
\sum y_i^2,\quad \sum x_iy_i
$$

这些状态可以得到滚动均值、方差、协方差和相关系数。

股票相对市场的 Beta 为：

$$
\beta=\frac{\operatorname{Cov}(R_{stock},R_{market})}
{\operatorname{Var}(R_{market})}
$$

计算时必须处理市场方差接近零的情况。

## 五、并非所有股票指标都是定长滑窗

有些指标使用有限窗口，有些指标使用递推平滑，不能混为一谈：

| 指标 | 是否为普通定长滑窗 | 原因 |
| --- | --- | --- |
| SMA | 是 | 明确使用最近 `k` 个值 |
| 滚动 MSE | 是 | 明确使用最近 `k` 个误差 |
| 滚动方差 | 是 | 明确加入新值并删除旧值 |
| 布林带 | 是 | 基于定长均值和标准差 |
| 滚动 VWAP | 是 | 基于窗口内成交额和成交量 |
| EMA | 否 | 使用历史 EMA 递推，不严格删除某个旧值 |
| MACD | 否 | 由不同周期的 EMA 构成 |
| Wilder RSI | 否 | 通常使用 Wilder 平滑递推 |

EMA 的典型递推为：

$$
EMA_t=\alpha x_t+(1-\alpha)EMA_{t-1}
$$

旧数据的影响会指数衰减，但不会在经过 `k` 个位置后突然离开窗口，因此它属于指数平滑，而不是严格的定长滑窗。

## 六、监控与可观测性

服务监控经常需要最近一段时间的指标：

- 最近 5 分钟请求数；
- 最近 1 分钟错误率；
- 最近 1000 次请求的平均延迟；
- 延迟的 P95、P99；
- 最近一段时间的超时率。

错误率可以写成：

$$
ErrorRate=\frac{ErrorCount}{RequestCount}
$$

窗口进入新请求时更新请求数和错误数，旧请求过期时撤销对应贡献。

平均值容易增量维护，但 P95、P99 等分位数不能只靠一个累加变量。常见方案包括：

- 有序多重集合；
- 双堆与延迟删除；
- 直方图；
- t-digest、KLL 等近似分位数结构；
- 按时间桶聚合后合并。

工程上经常需要在精度、内存和更新速度之间取舍。

## 七、网络限流

滑动窗口可以用于限制某个用户或客户端在最近 `T` 秒内的请求数量。

### 精确滑动日志

为每个用户保存请求时间戳队列：

```text
收到请求
删除队首所有早于 currentTime - T 的时间戳
如果队列长度达到限制，则拒绝
否则加入当前时间戳并放行
```

优点是准确，缺点是高流量用户会保存大量时间戳。

### 滑动窗口计数器

把时间分桶，只保存当前桶和前一个桶的计数，并根据当前时间在桶中的位置进行加权估算。

它比精确日志节省内存，但结果是近似值。大规模分布式限流还需要考虑：

- 多节点之间的状态一致性；
- 时钟偏差；
- Redis 等共享存储的原子更新；
- 热点键；
- 窗口边界附近的突发流量。

## 八、流处理与实时聚合

Kafka、Flink、Spark Streaming 等系统会把无界数据流切成有限窗口进行计算。

常见窗口包括：

### 滚动窗口 Tumbling Window

窗口互不重叠，例如：

```text
[00:00, 00:05)
[00:05, 00:10)
[00:10, 00:15)
```

适合每 5 分钟生成一次独立报表。

### 滑动窗口 Sliding Window

窗口可以重叠。例如窗口长度为 10 分钟，每 1 分钟计算一次：

```text
[00:00, 00:10)
[00:01, 00:11)
[00:02, 00:12)
```

### 会话窗口 Session Window

窗口由活动间隔决定。如果一段时间没有新事件，则认为会话结束。

流系统中还必须区分：

- **处理时间**：系统实际收到事件的时间；
- **事件时间**：事件自身携带的发生时间；
- **水位线**：系统对事件时间进度的估计；
- **迟到数据**：窗口结束后才到达的事件。

这已经超出普通数组双指针，但核心思想仍然是维护一个会随时间进入和过期的数据集合。

## 九、传感器与信号处理

滑窗可以用于：

- 温度、压力、振动数据的移动平均；
- 短期噪声平滑；
- 局部均值和标准差；
- 异常值检测；
- 峰值和突变检测；
- 设备近期状态评估。

例如计算滚动 Z-score：

$$
z_t=\frac{x_t-\mu_t}{\sigma_t}
$$

当 $|z_t|$ 超过阈值时，可以标记当前采样点异常。

工程上需要注意：当前样本是否应该包含在计算 $\mu_t$ 和 $\sigma_t$ 的窗口中。若包含，异常值本身会影响基准；若使用前一个窗口，则更适合检测“新样本相对历史是否异常”。

## 十、日志、安全与行为分析

滑窗还可以检测：

- 最近 10 分钟登录失败次数；
- 短时间内来自同一 IP 的大量访问；
- 用户近期交易频率异常；
- 一段时间内相同错误日志集中爆发；
- 连续事件序列是否触发安全规则。

这类系统经常需要按照用户、设备或 IP 分组，为每个键分别维护窗口状态。主要工程难点是：

- 键数量可能非常大；
- 长时间不活跃的键需要清理；
- 状态需要设置 TTL；
- 分布式分区必须保证同一键的事件进入同一处理节点；
- 状态丢失后如何恢复。

## 十一、环形缓冲区

对于按数量固定的窗口，没有必要每次移动整个数组。可以使用长度为 `k` 的环形缓冲区：

```c
typedef struct {
    double *values;
    int capacity;
    int count;
    int next;
    double sum;
} RollingMean;

double rollingMeanAdd(RollingMean *window, double value)
{
    if (window->count == window->capacity) {
        window->sum -= window->values[window->next];
    } else {
        window->count++;
    }

    window->values[window->next] = value;
    window->sum += value;
    window->next = (window->next + 1) % window->capacity;

    return window->sum / window->count;
}
```

这里在窗口尚未填满时，分母使用当前 `count`。实际系统也可以选择在收满 `k` 个样本之前不输出指标。

环形缓冲区的特点是：

- 固定内存 $O(k)$；
- 插入和删除均为 $O(1)$；
- 不需要移动数组元素；
- 可以直接找到即将过期的数据。

## 十二、不能直接相减的窗口指标

并不是所有状态都满足：

```text
新状态 = 旧状态 + 新元素贡献 - 旧元素贡献
```

例如窗口最大值。如果最大值正好离开窗口，仅保存一个 `maxValue` 无法知道新的最大值是什么。

不同指标需要不同结构：

| 指标 | 常见实现 |
| --- | --- |
| 和、平均值、MSE | 累加器加环形缓冲区 |
| 最大值、最小值 | 单调队列 |
| 中位数 | 双堆、平衡树或有序多重集合 |
| 分位数 | 有序结构或近似摘要 |
| 不同元素数量 | 哈希表加引用计数 |
| Top K | 堆、计数表或流式近似算法 |

滑窗确定的是数据进入和过期的规则，数据结构决定窗口状态如何高效维护。

## 十三、工程实现中的关键问题

### 1. 窗口未填满

需要明确：

- 使用当前样本数作为分母；
- 返回“数据不足”；
- 使用缺失值填充；
- 等窗口填满后再输出。

### 2. 缺失值与异常值

必须决定 `NaN`、空值和异常值是忽略、填充、截断还是使整个窗口结果无效。

### 3. 数值稳定性

大量浮点加减会累积误差。可以定期从窗口数据重新计算状态，用批量结果校正增量状态。

### 4. 时间乱序

按时间滑窗时，事件可能延迟或乱序到达。需要决定是否允许修改已经输出的窗口结果。

### 5. 并发安全

多个线程更新同一个窗口时，需要锁、原子操作、单线程事件循环，或者按键分区避免共享写入。

### 6. 状态持久化

持续运行的流系统需要考虑进程崩溃后如何恢复窗口，包括检查点、日志重放和幂等处理。

### 7. 内存上限

按时间窗口保存原始事件时，窗口内元素数量可能没有固定上限。必须设置容量限制、降采样策略或分桶聚合。

## 十四、如何判断一个指标适合滑窗

可以依次检查：

1. 指标是否只关注最近 `k` 条或最近 `T` 时间的数据？
2. 新数据进入时，状态能否增量更新？
3. 旧数据过期时，它的贡献能否被删除？
4. 若不能直接删除，是否有单调队列、堆或有序结构可用？
5. 是否要求精确结果，还是允许近似？
6. 窗口按数量还是按时间定义？
7. 是否存在乱序、迟到、缺失或重复数据？
8. 数据规模是否允许保存窗口内的原始值？

最通用的判断是：

> 指标能否通过“加入新数据、删除过期数据、查询当前状态”持续维护？

如果可以，滑动窗口通常能够把重复的批量计算转化为高效的实时增量计算。
